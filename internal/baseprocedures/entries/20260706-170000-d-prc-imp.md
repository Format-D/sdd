The implementation procedure runs committed work — a plan, directive, or activity — as a working loop around host work: the building happens outside the engine, and the procedure holds the discipline around it. It serves the work contract, settles the run mode with the user and creates the WIP marker itself, takes progress check-ins between slices, routes undecided design choices into dialogue instead of improvisation, and closes in order — code committed, done signal recorded, marker removed, evaluation offered.

The run holds one branch fact of its own, `baseBranch`, the marker's home. Every other read and write — captures during work, the closing done, the reads that resolve them — follows the session's branch binding: declared when the host enters the work branch, cleared when the host returns to base. The binding is a stack the agent pushes and pops around the work; the procedure never copies it.

## unit: anchor

Establish what is being implemented — a resolved anchor advances this step, and a seeded one (dispatched from an engagement, or passed as a known entry ID) auto-advances past this prompt.{{if .anchorHint}} The user's pointer: "{{.anchorHint}}".{{end}} Report `anchor`: the plan, directive, or activity this run realizes.

- **Entry ID given**: report it directly.
- **Pointer or phrase given**: search the graph from several angles and settle the centre with the user before reading the contract. Recency does not resolve an anchor — ambiguity resolves in dialogue.

## unit: contract

The work and its surroundings, served in full:

{{.entryChains}}

**The contract is the union.** Read the acceptance criteria and every augmenting directive in the downstream chain — together they are what done means; partial done signals in the chain mark what is already covered. Synthesize `contract`: each outstanding item with its status, and your readiness read — are there enough decisions to build against? Prefer shrinking scope over building into the unknown; name any hole plainly — the next step has a hold option for capturing the missing decision before work starts.

**Widen before you build.**{{if .widenReport}} Grounding was inherited from the dispatching move:

{{.widenReport}}

Extend it only where the work reaches beyond what was inspected, appending to `widenReport`.{{else}} Search the graph for what bears on this work — neighbors that constrain it, signals captured near it, prior partial attempts. Record the searches and what they surfaced in `widenReport`; inspect promising results in full before they shape the work.{{end}}

## unit: baseTarget

Resolve the concrete branch that carries coordination for this run. Report `baseBranch` explicitly before the marker is created. Use repository evidence; never infer it from cwd, never assume `main`, and do not substitute the configured ordinary-capture default. This is the only branch the procedure holds; the work branch, when the run gets one, lives in the session binding.

## unit: setup

How should this run be executed? The mode is the user's call — recommend one for the scope, then put it to them; it cannot be inferred:

- **inPlace** — contained changes, directly on the main line.
- **branch** — isolation in the same directory.
- **worktree** — isolation in a separate directory; the run proceeds autonomously and the user confirms the merge.
- **quick** — the user judges it too small to track; the only mode without a marker. Everything else — contract, check-ins, the recorded done — still applies.
- **hold** — a needed decision is missing: capture it first (the answer seeds your grounding into that capture), then return here to pick a mode.
- **abort** — wrong anchor or wrong time; abandons the run.

A tracked mode collects `wipDescription` — one line naming the work — and creates the exclusive WIP marker on the anchor as part of the answer; the engine removes it again after landing. Relay the user's answer verbatim.

**Entering the work branch is host work**, done after the answer — a branch switch or worktree creation your harness performs its own way. Once the host is on the work branch, declare that branch as the session branch binding through the engine's session branch-binding capability: a routing declaration that sends this run's reads and captures to the branch the work is on, not a checkout operation. In-place and quick runs stay on `baseBranch` and declare nothing.

## unit: work

You are between slices of host work. Sanity-check each slice as you go — problems surface cheapest early. Reads and captures follow the session binding named in the served session framing; if the host is on a work branch the framing does not name, declare it before capturing anything. The junction:

- **continue** — report `progressNotes` and keep building: the full running record — what landed (with commit hashes), what is next, which decisions were made in dialogue along the way. Keep it current; it is what a later session resumes from, and stale notes mislead better than no notes.
- **blocked** — the work hit a choice no decision covers. Do not decide alone, and do not capture yet: present the roadblock to the user in plain words, propose one or more ways forward, and settle it in dialogue. What crystallizes becomes zero or more captures — an augmenting directive, a directive, a gap, a question — each played back and confirmed the normal way; the blocked answer seeds your grounding into them. Report `roadblock` with the stop, then return here to continue or to pause.
- **conclude** — the contract is met, or the run deliberately stops short (say which): move to recording.
- **abandon** — the user drops this run: the marker is removed on `baseBranch` and the run ends without a done. Only on the user's explicit word; observations made along the way are still captured as ordinary entries. If the host is on a work branch, clear the session binding once it has returned to base.

Pausing needs no answer: the run stays here, resumable, with `progressNotes` carrying the pickup.

## unit: record

Close the loop in order — the artifacts must outlive this session:

1. **Commit the code**, then capture the closing **done signal** as the dispatched sub-move — enter capture with `kind` done and `closes` naming the fulfilled commitments. It lands where the work is: on the branch the session binding names, so it reaches `baseBranch` together with the code. The body cites the commit hashes, addresses every acceptance criterion and augmenting commitment (or names what stays open — a partial stop records the same way, honest about what remains), and carries work-shape `topics` for the kind of work concluded: `implementation/<...>`, e.g. `implementation/engine` or `implementation/skill-text`.
2. Report `doneEntry` — the captured done signal's ID. A tracked run then enters the landing junction with the marker still present on `baseBranch`; quick runs skip it.

## unit: landing

The work branch now carries code and its completion evidence together. Present the landing read: which acceptance criteria are met, deviations, inner and outer judgment, and merge-ready or hold. The merge or in-place landing is host work, and it runs in this order:

1. The host places the work on `baseBranch` — merge, or the in-place commit.
2. The host returns to `baseBranch`: the checkout is back on base, or the base checkout is the one in use again.
3. If this run declared a work branch as the session binding, clear it now, through the engine's session branch-binding capability, before the work branch or worktree is removed. From here every read of this run follows base again; the branch and worktree themselves stay until the host removes them.
4. Report the user's word: **landed** means the host is back on `baseBranch` with the work on it, so the engine removes the marker there; **defer** keeps the marker and this resumable landing junction intact.

Relay the user's answer verbatim. Report `landed` only after steps 1 to 3 — a run still bound to a work branch that no longer has a checkout cannot be read.

## unit: closeout

The work is recorded and the marker is gone. One more offer — evaluation is its own work, recorded as its own entry, and this is the cheapest moment to start it: the run's grounding seeds it, and the fresh done signal is its anchor. Put it to the user: **evaluate** starts the evaluate procedure on the just-captured done; **finish** ends the run — the learning loop stays open for a later session or another participant.
