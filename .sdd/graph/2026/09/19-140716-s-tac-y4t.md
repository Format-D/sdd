The engine hands a failed mutation back to the agent as a bare tool error carrying executable retry and cancel calls, and the agent acted on it without the user knowing. Observed on 2026-09-15 while evaluating the capture-publication delivery (20260915-085829-s-tac-awi) in a hosted composition: a one-shot fault withheld the Git service's success reply after the entry had been committed, the MCP call returned a tool failure, and the agent retried without a word to the user. Publication recovery itself worked, the entry landed once and the capture completed; Christopher, the user in that session, reported afterwards that he had never been asked. The failed response was not retained, so its shape is read from the code at that revision, unchanged at `8681c6f6`: `next` returns the failure as a Go error, the SDK wraps it as `isError` with the text in `content[0].text`, and that text is the engine's continuation string, the command name, a dump of the recorded values, the two `next(...)` calls in tool syntax and the publication clause, with no goal, no owner and nothing about the user. Resume serves the same string twice, in `pending_operation.instructions` and in `instructions`. Draft playback and the pre-flight override, by contrast, arrive as user choosers: a goal that says to ask, a `kind: user` marker, prose that says to wait and relay, and a required `userWords` field.

Expected, per 20260829-113416-d-cpt-nut: a handed-back failure returns as a position the agent can advance from, named and with what to do about it, so that trying again is a choice made in the dialogue and whether to keep waiting is the user's call; that directive rejected returning a bare error precisely because an error invites the agent to look for something to fix. 20260914-113737-d-cpt-qst requires explicit continuation beyond bounded automatic attempts and a cancellation that leaves effects in place, without naming who continues. The deviation: the shipped recovery serves the mechanics of continuation and nothing of its ownership, so the agent's silent retry followed the surface as served rather than defying it. The tool-call syntax in the same text is already among the review findings in 20260915-093114-s-tac-ixt.

Candidate direction, agreed in the dialogue that captured this and left to a separate decision: neither a question for every glitch nor a silent retry. Told from the user's side, a dropped connection on the train is retried with one sentence said; a provider outage is retried, then handed over when it keeps failing; exhausted credits are not retried at all; a timeout after the write landed is retried because retry is safe; and a pending operation survives to the next day's resume. The instruction that serves this is scoped to the failed operation, generic over every operation, and comes back as a normal serve with the error and refs as fields. Its agreed text, verbatim:

> This operation did not finish. Tell the user in a sentence. Retry, saying so, when trying again can help; when it cannot, or has stopped helping, the user decides. It can stay pending. Retry is safe: it reuses the recorded input, and effects already applied are recognized, not repeated. Cancel leaves what exists in place.
