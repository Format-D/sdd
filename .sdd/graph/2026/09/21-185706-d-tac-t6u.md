An unfinished operation and a cancelled one return two distinct serves, and this fixes what each carries beyond the wording 20260919-141340-d-tac-qws settled. The **pending-operation serve** is returned while an operation has not finished — at the moment of failure, and again on every resume until it is retried or cancelled. The **cancellation serve** is returned once a cancellation is accepted, and lands on the interaction the operation was dispatched from. Where 20260919-141340-d-tac-qws says the failure arrives as a normal position rather than an error, it means this serve: `position` names the event-log sequence number alone, which is what `retry_ref` and `cancel_ref` carry, and using it for what a call returns confuses the two. Both serves were driven live and read from the wire; the responses are in [observed surfaces](./21-185706-d-tac-t6u/observed-surfaces.md).

**The pending-operation serve does not invite a report.** It carries no `report_schema` and no `missing`, and its goal is the continuation goal — carry the operation through by retrying, or cancel it to unblock the instance. Today it serves `goal: "provide the missing report fields"` with the full assemble schema beside it at a pending `publish` step; an agent that follows that goal sends a report and is refused. The step's own instruction unit is suppressed for the same reason: while the operation is unfinished, that unit describes work that cannot proceed. The cancellation serve is the opposite case and is already right — it lands on a live step, so its chooser and schema belong there.

**Each serve's prose arrives once.** On that serve's `instructions` and nowhere else — not repeated into the `pending_operation` or `cancellation` field beside it, and never through the diagnostics channel, which renders it under `Gate held:` as though a predicate had failed. Observed on resume: four occurrences for an unfinished operation, two for a cancellation. 20260919-140716-s-tac-y4t records two, read from code; fourfold is what the wire shows.

**Structured values are fields, never prose.** No `map[branch:main entryId:…]` rendering inside a sentence, and no `next(instance=…, retry_ref=…)` tool syntax, which 20260707-134311-d-cpt-476 forbids in served text and 20260915-093114-s-tac-ixt already recorded as a finding.

**The failure’s error is live-only.** It is present at the moment of failure and absent after a resume, because a failed attempt changes no state and nothing is appended for it: the intent stays unfinished exactly as recorded. This qualifies the identity 20260919-141340-d-tac-qws claims between failure and resume — the prose, the operation name and the refs are identical, the error is not carried across. Durability is earned by a captured entry and never by session bookkeeping (20260727-224047-d-cpt-u8o), and a clearly defined loss with a converging path is acceptable for session state. What a retry needs survives; the diagnosis does not.

**The cancellation serve names what it left.** It must say which entry was written, so the agent can tell the user rather than report that unnamed effects remain. Cleaning up that residue is out of scope here and stays future work.

**A transition other than retry or cancel, while an operation is unfinished, is refused rather than answered with a serve.** The refusal states that only retry and cancel are accepted, instead of repeating the continuation mechanics. The distinction is 20260829-113416-d-cpt-nut’s: the failure itself is handed back as something the agent advances from, while an agent attempting something else has supplied bad input and must be told so.
