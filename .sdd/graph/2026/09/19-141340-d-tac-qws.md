When an engine operation fails after the engine's own attempts, the agent is served this text verbatim, with the operation's name, its error and its retry and cancel refs as fields beside it:

> This operation did not finish. Tell the user in a sentence. Retry, saying so, when trying again can help; when it cannot, or has stopped helping, the user decides. It can stay pending. Retry is safe: it reuses the recorded input, and effects already applied are recognized, not repeated. Cancel leaves what exists in place.

It arrives as a normal position, not as an error, identical at the moment of failure and after resuming a session while the operation is still pending. It is the only prose on that position, scoped to that operation and the same for every operation the engine runs. It answers 20260919-140716-s-tac-y4t, where the agent retried without a word because the failure came back as a bare error with commands. It is what the handed-back position of 20260829-113416-d-cpt-nut says at the moment it is handed back, under the explicit continuation, safe retry and no-rollback cancellation of 20260914-113737-d-cpt-qst.

Why one text rather than a rule per failure: the agent sees the error and the user, the engine sees neither, so the agent judges whether trying again can help; a fixed count or a list of failure modes is wrong for the case nobody planned. Why the user is named only at the edge: a question for every glitch teaches the user the tool is fragile, a silent retry teaches them nothing. Why the safety sentence: without it an agent hesitates to retry a timeout that may already have landed, which was the observed case. Fulfilled only when the session delivering it has looked at the complete response the engine's MCP server returns, at the moment of failure and after resuming a session, and seen this text arrive correctly together with the structured fields; checking the refs alone, or the text alone, is not fulfilment.
