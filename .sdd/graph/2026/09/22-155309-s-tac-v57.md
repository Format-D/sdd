The code of one engine command is split across `WorkflowSession` and `Application` by layer instead of bundled per command, so both types grow with every command function.

Observed in the review of PR #17 at 6cd3cd4d: the capture command's three functions, `prepareWorkflowNewEntry`, `runWorkflowNewEntry` and `reportWorkflowNewEntryEffects` (the effects report of 20260921-194758-d-tac-7mh), are methods on `WorkflowSession` in two files, registered by name in `workflow_registry.go`, while the storage calls they share, `CreateEntry` and `entryPublicationExists`, sit on `Application`. None of the three is reusable apart from the others. Expected, stated by Christopher in that review: one type per command bundling what the command does, built by a factory to which `WorkflowSession` and `Application` pass their dependencies and which returns the `engine.Command`, so the two composition types keep core knowledge and stop growing per command, in the spirit of the composition root 20260830-114446-d-cpt-xc3. Deviation: split by layer, not by command.

Candidate remedy, unsettled: a `newEntry` command type in `pkg/application` constructed with the session's binding, identity and application, whose methods are the registered prepare, run and effects, and the same shape for every command with a prepare step. The ability-model redesign 20260726-195739-s-cpt-hcp names the separation of ability declaration from session-scoped wiring as neighbouring territory.
