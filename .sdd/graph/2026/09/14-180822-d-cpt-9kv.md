The implementation procedure holds one branch fact, `baseBranch`, the marker's home; every other read and write follows the session's effective branch. Work-time captures reach the branch the work is on because the agent declares the session binding when the host enters it and clears it when the host returns to base, and `landed` is reported after that return. This supersedes 20260713-214251-d-prc-pop, answers 20260902-160151-s-tac-mtv, and sets the procedure's shape for local and remote session hosts alike.

Kept from the superseded lifecycle: the marker is created on base so everyone sees the work is taken; captures during work, the closing done included, land where the work is and reach base with it; the marker is removed on base only after the user reports landing; commit hashes are evidence, never gates. Changed: `workBranch` is no longer procedure state. It duplicated the session binding of 20260722-112853-d-tac-ln1, and the target rule ranked the persisted copy above the binding, so after the host returned to base the instance still read the work branch. Without a worktree that fails on every run, since merging means checking out base. The binding is the stack: push on entering the work branch, pop on return. Landed then means the host is back on base; the engine removes the marker there, and the closeout, evaluation dispatch, and any resume read base.

Two independent facts shape a run. Where the graph is authoritative is the repository and branch, never the server hosting the session; 20260713-214050-d-cpt-65i holds and targets stay explicit. What the agent can do is a declared session property, following the non-interactive property of 20260827-232430-d-cpt-voa: the client declares a coding host with a checkout when it opens the session; procedure text branches on it for commit, branch, and merge guidance; the session shell offers the implementation move only when it is present. A chat or web client reports finished work and captures gaps and questions; it does not run implementation. Branch and worktree operations remain host work per 20260628-130403-d-cpt-h4l.

A remote session host over an embedded graph must support work on a branch. The remote session accepts the declared work branch as a declaration it cannot verify against a checkout, and each capture is an accepted intent for that branch, delivered under 20260914-113737-d-cpt-qst by pushing to the canonical remote or by handing the bytes to the coding agent to commit. The sync experience around an unpushed branch is a separate story; this decision requires only that the model permits the workflow.

Where no code branch exists, a remote store stays branchless: marker, captures, and done on base. An observation made during discarded work is still an observation, and the done is the only entry tied to the work's fate. 20260715-113417-s-cpt-vxd stays open as a question whether logical branching is ever needed, not as a gap to build.

Also required: the engine acquires no graph for a command that declares no reads; a failed read names the read and the state field that chose the branch, since `mutation target branch` reports a read as a write; the landing step of 20260706-170000-d-prc-imp says merge, return to base, then report `landed`; the procedure gains an abandon path after setup that removes the marker on base.

Rejected: instructing the agent to report before removing the worktree, because no such order exists without one; mimicking Git branches in remote stores, because nothing forces the need; inferring the host from client metadata, because it is ambient.

Fulfilled when the procedure, target rule, declared host property, and remote branch delivery ship, with a regression for landing after the sole checkout returns to base.
